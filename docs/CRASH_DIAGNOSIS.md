# 2026-10-07 音频结束回调崩溃排查

## 已确认的证据

- 用户在旋转、硬降或消行过程中遇到意外退出。
- 报告显示主线程 `EXC_BAD_ACCESS`，调用栈为 `objc_msgSend → __NSThreadPerformPerform`。
- 原始线程寄存器中的目标选择器为 `finishedPlaying:`，将排查范围缩小到音频结束回调。
- 原实现根据 `isPlaying` 清理播放器，并在停止、重开和播放数量达到上限时移除播放器引用。

原始崩溃暂未稳定复现；不能仅凭系统栈确定具体是哪一个播放器或系统内部对象被访问。本次修改是针对音频对象生命周期的防护修复，不将无崩溃的测试结果等同于原始问题已被完全证明解决。

## 修复

操作音效与消行音效改用 `SoundVoicePool`：

- 已分配的播放器在音频服务存活期间始终保留，结束、停止和重开只停止播放，不释放播放器。
- 每种音效最多保留两路播放器，后续播放复用这些对象。
- 操作音效最多保留 6 个播放器、同时播放最多 4 路；消行音效最多保留 8 个播放器、同时播放最多 8 路。
- 达到播放上限时停止最早播放的声部，但保留其对象，避免把声音结束状态当成回调队列已清空的证明。
- 保留原有开关、音量、旋转限频、静音事件消费和消行 BGM 混音行为。

## 验证

`swift test --filter AudioLifetimeTests` 覆盖自然结束、重开、停止、连续播放和声部复用。

生命周期回归测试在旧实现上出现两个断言失败：重开后应保留的两类播放器数量均从 1 变为 0。此测试捕获的是提前释放的生命周期边界，不是原始 SIGSEGV 的稳定复现。

修复后完整测试共 42 项通过；使用 `NSZombieEnabled=YES` 运行音频生命周期测试，检查是否报告向已释放对象发送消息。实际游戏游玩仍需持续观察；若再出现退出，应对照新的崩溃栈继续定位。

## 后续日志分析

设置 → 日志 → 打开日志文件夹。事件包含进程会话 ID、时间、单调时钟、对局 ID、操作前后方块与得分状态、音效池类别及播放结果；日志按大小轮转。启动时检查上次会话是否正常关闭，强制退出也会留下未正常关闭标记，因此该标记不能单独证明崩溃。下一次异常请保留 JSONL 日志及 macOS 崩溃报告，对照最后一次 action_begin / action_completed 与 audio_play_begin / audio_play_completed 缩小范围。
